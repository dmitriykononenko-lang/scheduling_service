# Архитектура

Документ описывает устройство каркаса и принятые решения. Опирается на ТЗ
(разделы §5–§9). По мере развития фич дополняется.

## Обзор

```
            ┌──────────────┐         ┌───────────────────────────┐
  Браузер → │  Next.js SSR │ ──REST→ │        FastAPI (API)       │
            │  (frontend)  │         │  app/api/v1/*              │
            └──────────────┘         │  auth · event-types ·      │
                                     │  public · health           │
                                     └───────┬──────────┬─────────┘
                                             │          │
                                   async SQLAlchemy   enqueue
                                             │          │
                                       ┌─────▼────┐  ┌──▼──────────┐
                                       │PostgreSQL│  │ Redis broker│
                                       └──────────┘  └──┬──────────┘
                                                        │
                                          ┌─────────────▼─────────────┐
                                          │ Celery worker + beat       │
                                          │ напоминания · синк календ. │
                                          │ доставка webhooks (ретраи) │
                                          └────────────────────────────┘
```

- **Stateless API** (§5): горизонтально масштабируется; состояние — в PostgreSQL/Redis.
- **Фоновые задачи** вынесены в Celery: напоминания, опрос календарей, доставка webhooks
  с ретраями. Периодика — через Celery beat (§6.1).

## Ключевые решения

### Часовые пояса (§5)
Все моменты времени хранятся в `TIMESTAMPTZ` (UTC). Конвертация в пояс организатора/гостя —
на отображении. У `User` и `Booking` есть поля таймзоны; расчёт слотов учитывает переходы
на летнее/зимнее время на стороне приложения (zoneinfo).

### Защита от двойных броней (§4.2 КП, §7)
Реализована на уровне БД — самый надёжный вариант при гонках:

```sql
ALTER TABLE bookings ADD CONSTRAINT excl_bookings_host_no_overlap
EXCLUDE USING gist (
    host_id WITH =,
    tstzrange(start_utc, end_utc, '[)') WITH &&
) WHERE (status IN ('confirmed', 'pending_payment', 'rescheduled'));
```

- Расширение `btree_gist` позволяет смешивать `=` (по `host_id`) и `&&` (пересечение диапазонов).
- Полуинтервал `[)`: смежные встречи (конец одной == начало другой) не считаются пересечением.
- Условие `WHERE` исключает отменённые/завершённые брони из проверки.

Перенос брони (§4.5 КП «атомарно») выполняется в одной транзакции: старый слот переводится
в `canceled`/`rescheduled`, создаётся новый — ограничение гарантирует отсутствие коллизий.

### Идемпотентность платежей (§5, §9)
- `payments.idempotency_key` (unique) — безопасный повтор создания платежа.
- `uq_payments_provider_external_id` — один внешний платёж эквайера = одна запись.
- Сырые вебхуки эквайера сохраняются в `payments.raw_payload` для аудита.

### Безопасность (§9)
- Пароли — argon2 (`argon2-cffi`), с прозрачным rehash при устаревании параметров.
- Доступ — JWT (HS256); продовый `SECRET_KEY` ≥ 32 байт.
- API-ключи хранятся только в виде SHA-256 хеша; пользователю ключ показывается один раз.
- Webhooks подписываются HMAC (секрет на каждый эндпоинт) — доставка в Ф2.

### Данные и миграции
- UUID-первичные ключи (`gen_random_uuid()`).
- Перечисления — VARCHAR + CHECK (`native_enum=False`), чтобы не упираться в `ALTER TYPE`.
- Единая naming convention для индексов/ограничений → стабильные имена в Alembic.
- `alembic check` в CI ловит расхождение моделей и миграций.

## Соответствие 152-ФЗ (§9)
Хостинг и БД с персональными данными граждан РФ размещаются в РФ (Yandex Cloud / VK Cloud /
Selectel). Каркас от облака не зависит (Docker), решение о провайдере — на этапе инфраструктуры.
